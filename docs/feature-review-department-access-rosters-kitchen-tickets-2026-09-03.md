# Feature Review — Department Access Control, Rosters & Kitchen Tickets

**Review date:** 2026-09-03
**Scope:** All code introduced by commits `48c01b3` (kitchen-to-distro pickup notifications), `5c46567` (department access control, default workspace routing, daily staffing rosters), evaluated against `main` at HEAD. 17 files, 5,144 new lines: `access-control.helper.ts`, `departments.{controller,service,dto,module}.ts`, `kitchen-distro-fulfillment.{controller,service}.ts`, `daily-roster.{controller,service,dto}.ts`, 3 spec files, 2 migrations (`20260903160000`, `20260903180000`), `app/stadium/distro-pickup.tsx`, `app/stadium/kds.tsx`, 2 components.
**Method:** Full read of every service/controller/DTO/migration file, RLS policy inspection, test-suite content audit (not just pass/fail), typecheck + full unit-suite run (939 tests, all green) against a local PostgreSQL 18 instance. Every finding below is anchored to a specific file and line, not inferred.

---

## 1. Executive Outcome

**`NOT READY`**

The department-based access-control module (`access-control.helper.ts`) is well-designed and well-tested **in isolation** — but it is not wired into either feature it was built for. `canAccessResource`, the function that enforces Suites/Clubs/Catering/Concessions/Culinary segmentation, **is called by zero application code** (confirmed by repo-wide grep). Kitchen tickets use only a facility/zone-level gate (`assertOperator`) with no department awareness at all. Daily rosters use the narrower `assertCanManageDepartment` in most places, but two view/export endpoints and one submit endpoint skip it entirely, and two update endpoints don't verify the resource they mutate belongs to the resource they authorized against (IDOR). Database RLS provides no backstop for any of this — every new table's policy is facility/zone-scoped only, with no department dimension, so a correct RLS design was never possible without the missing checks. This is exactly the "looks complete, fails under adversarial conditions" pattern the review was commissioned to catch.

## 6. Final Gate

**`NOT READY`**

The two Critical-severity classes of finding — department authorization never invoked for kitchen tickets (F-01/F-02), and missing/IDOR-vulnerable authorization on three roster endpoints (F-03/F-04/F-06) — mean the feature as it stands does not meet its own stated visibility matrix for any of Suites, Clubs, Catering, Culinary, or Concessions, and allows cross-department payroll-adjacent record tampering. These are not edge cases; they are the primary endpoints (`GET`/list/submit/update) of each feature.

Do not deploy to staging with real venue/department data until priority-1 and priority-2 items above are fixed and independently verified with the specified negative tests — not just a re-read of the code. Priority-3 items (state-machine/race/validation gaps) should land before any production pilot with concurrent kitchen or roster traffic, since they are readily triggerable by normal double-tap/retry behavior, not just deliberate attack.

The underlying `access-control.helper.ts` module and the department-membership model it's built on are sound engineering — the fix is integration, not a redesign.
